# Отдельные описания наборов и повторное использование логики

## Цель и согласованные требования

TouchBar разделяется на три слоя:

1. **Движок** выбирает наборы по контексту, строит и рисует интерфейс,
   доставляет события, управляет временем жизни и предоставляет системные
   функции через существующий брокер.
2. **Логика** обрабатывает действия, ведёт состояние, подписывается на события
   и обращается к конкретным функциям движка. Она не задаёт расположение кнопок.
3. **Описание набора** хранится в отдельном TOML-файле: условия включения,
   расположение, внешний вид, привязки состояния и обработчиков.

Другой набор может использовать тот же код логики. Это не означает общий
экземпляр: состояние, запросы, подписки и презентации у наборов независимы.
Добавление набора с уже существующими действиями и изменение его расположения
не требуют пересборки Wasm. Новое поведение требует изменения второго слоя.

Это рефакторинг существующего проекта. AUR-рецепт, установка сервиса, запуск
постоянного сервиса и вложенный неотслеживаемый checkout `touchbar/` вне работы.

## Что есть сейчас

- `touchbar-profile-config` загружает один `profiles.toml`, описывающий
  композицию готовых plugin items. Описаний кнопок и ссылок на файлы нет.
- `plugins/*/src/lib.rs` одновременно создают UI через `ViewBuilder` и
  обрабатывают события. Например, Browser Navigation и Text Formatting
  находятся вместе в `plugins/app-actions/src/lib.rs`.
- `touchbar-plugin-host` запускает Wasm, проверяет дерево UI, управляет
  взаимодействием и вызывает брокер. `sessiond` получает пиксели, а не
  привилегированное дерево виджетов.
- Менеджер уже запускает отдельный процесс для каждого item. Это подходящая
  граница независимого состояния набора.
- Манифест, Wasm и изображения входят в проверяемые артефакты пакета.
  Новый файл набора должен участвовать в тех же проверках.

## Выбор подхода

**Выбран общий декларативный renderer в plugin-host и отдельный Wasm-контракт
для логики.** Сохраняются процессы, GPU UI, брокер и проверка разрешений.
Renderer читает описание и строит обычный `RetainedUi`; логика возвращает
значения состояния и запросы презентации, а не дерево кнопок.

Две альтернативы:

- Только разбить `profiles.toml` на включаемые файлы. Это полезно для композиции,
  но оставляет UI и действия вместе в Rust и не выполняет требование трёх слоёв.
- Загрузить произвольные нативные обработчики непосредственно в `sessiond`.
  Это проще для вызова функций, но меняет существующую границу изоляции и
  допускает падение обработчика в процессе сессии. Такой механизм не вводится.

## Границы компонентов

| Компонент | Ответственность |
| --- | --- |
| Новый `touchbar-set-config` | Строгая схема TOML, проверки ссылок, типов и размеров; без GPU и системных вызовов |
| Декларативный renderer в `touchbar-plugin-host` | Описание + состояние → `RetainedUi`; привязка событий к действиям |
| Новый WIT world `button-set-logic` | Конфигурация логики, именованные действия, состояние, lifecycle и host events |
| Общие Rust-модули в SDK/библиотеках логики | Повторное использование реализации между наборами и компонентами |
| `touchbar-plugin-supervisor` и существующие backends | Системные операции, разрешения, activation и учёт ресурсов |
| `touchbar-sessiond` | Композиция наборов, выбор по контексту, доставка lifecycle, обновление конфигурации |

Рисование остаётся в plugin-host. Новые описания не переносят UI в `sessiond`.
Старые world `plugin`, `visibility-aware-plugin`, нативные плагины и appearance
providers продолжают поддерживаться.

## Файлы и явное подключение

Пакет объявляет файлы наборов в манифесте, без сканирования каталога:

```toml
[runtime]
kind = "button-set-logic"
entrypoint = "component/actions.wasm"
world = "touchbar:plugin/button-set-logic@1.0.0"

[[sets]]
id = "browser"
file = "sets/browser.toml"

[[sets]]
id = "formatting"
file = "sets/formatting.toml"
```

Каждый файл описывает один основной item и, если нужно, его раскрытые панели.
Стабильные item IDs сохраняются. Для нового runtime список `sets` является
источником items; одновременное объявление старых `items` запрещено.
Один entrypoint используется обоими наборами, но инстанцируется отдельно.

Пример сокращённого, но определённого формата `sets/browser.toml`:

```toml
version = 1
id = "browser"
label = "Browser Navigation"
default_width = 240
logic_config = "browser"

[selection]
applications = ["firefox", "org.mozilla.firefox", "chromium", "google-chrome"]
enabled_by_default = true
priority = 0

[layout]
kind = "row"
spacing = 8

[[layout.children]]
kind = "button"
id = "back"
label = "Back"
symbol = "chevron.left"
enabled_from = "shortcuts_available"
on_activate = "back"

[[layout.children]]
kind = "button"
id = "forward"
label = "Forward"
symbol = "chevron.right"
enabled_from = "shortcuts_available"
on_activate = "forward"

[[layout.children]]
kind = "button"
id = "reload"
label = "Reload"
asset = "reload"
enabled_from = "shortcuts_available"
on_activate = "reload"
```

`logic_config` — именованный вариант конфигурации, проверяемый модулем при
инициализации. Реальный Browser-файл сохраняет весь нынешний список приложений.
`selection` использует существующую модель контекста; явные пользовательские
правила сохраняют приоритет над пакетными. Файл без `selection` доступен для
ручной композиции и не получает выдуманного правила выбора.

В пользовательском `profiles.toml` появляется необязательный `include` со
списком относительных файлов-фрагментов. Фрагмент содержит композицию одного
профиля и его правила; сами кнопки остаются в файлах наборов пакета.
Вложенные includes не допускаются. Порядок явный, дубликаты IDs — ошибка.
Пути нормализованы и не выходят за каталог основного файла. Существующий
монолитный формат продолжает работать.

Редактирование пакетного набора требует обновления установленного пакета,
как и изменение нынешнего манифеста. Пересборка компонента при этом не нужна;
обход неизменяемого plugin store для горячего редактирования не вводится.

## Контракт логики и общие функции

Логика экспортирует:

- `describe`: доступные действия с допустимыми видами событий, типы входов
  и поля состояния;
- `initialize`: item ID и ограниченная конфигурация → начальное состояние;
- `handle-action`: имя действия, вид события, типизированное значение,
  идентификатор контакта → обновление состояния/презентации;
- обработчики visibility, presentation и существующих broker host events.

Полей состояния четыре базовых типа: bool, число, строка и ограниченный список
записей этих типов. State update — проверяемый patch, не произвольная программа.
Имена, типы, длины и конечность чисел проверяются. Логика не возвращает layout.
При загрузке host проверяет каждую привязку действия и состояния по `describe`;
опечатка не превращается в молча неработающую кнопку.

Набор выбирает готовый модуль логики через runtime пакета и `logic_config`.
Например, Browser и дополнительный компактный Browser используют один Wasm
и разные файлы. Расширенная логика может включить общий Rust-модуль действий
и добавить свои обработчики: общий код не копируется в исходниках.
Динамическое связывание произвольных модулей разных пакетов не требуется для
этой реализации; у каждого набора один Wasm entrypoint и один владелец policy.

В SDK вводится типизированный фасад функций движка, использующий брокер:
`keyboard.shortcut(id)`, `media.subscribe()`, `media.command(player, action)`,
`audio.set_volume(value)`, `audio.toggle_mute()`,
`display.set_brightness(value)`, `power.set_profile(profile)`.
Для controls общая реализация запросов и разбора ответов переносится из
конкретного набора в адаптеры этих функций. Backend и существующие scope
проверки сохраняются; новый фасад сам по себе не выдаёт разрешений.

Медиаплеер хранит track ID, позицию и preview в логике; слайдер из TOML
передаёт ValueChanged/Activated/Released/Cancelled в именованный обработчик.
Seek отправляется через функцию движка с реальными player/track IDs.
Панели используют существующие presentation sessions и их lifecycle.

## Интерфейс, события и время жизни

Описание покрывает используемые первичными плагинами контейнеры, отступы,
кнопки, подписи, символы, изображения, индикаторы, слайдеры, scrubber и панели.
Динамические подписи/значения/доступность/видимость берутся из state bindings.
Для повторяемых элементов списка задаётся декларативный шаблон и стабильный
ключ. Цвета и размеры используют существующие theme roles и UI constraints.
Canvas-команды, если нужны нынешнему виджету, передаются как ограниченные
данные содержимого; размещение и события остаются в описании.

Маршрут: физический input → существующая обработка жеста → widget ID →
проверенная привязка из файла → действие логики → функция движка/брокер →
host event → обновление состояния → перерисовка.

На экземпляр набора создаются свой Wasmtime Store, логика и таблица ресурсов.
Совпадение entrypoint допускает повторное использование скомпилированного
Component, но никогда Store или живой логики. Скрытие доставляет lifecycle
событие; модуль закрывает ненужные подписки. Удаление/перезапуск завершает
запросы и ресурсы экземпляра. Существующее поведение при смене активного окна
и отмене контакта сохраняется.

## Проверки, обновление и ошибки

- Файлы наборов входят в `artifact_paths`, package digest/lock, проверку store
  и sealed descriptor bundle. Host в production не перечитывает непроверенный
  путь вместо переданных supervisor байтов.
- Разрешения принадлежат пакету логики. Повторное использование кода не
  переносит grants между пакетами и не расширяет scope по данным layout.
- Activation создаётся host из реального input; имя обработчика и значение
  из TOML не могут создать или продлить activation. В init/render системные
  эффекты запрещены; подписки допустимы в lifecycle через прежние проверки.
- Ограничения дерева/глубины/текста/списков не превышают существующие HostLimits.
  Каждый конфигурационный файл ограничен 256 KiB, include-граф — 64 файлами
  и общим размером 1 MiB. Неизвестные поля и небезопасные пути — ошибки.
- Пользовательские фрагменты читаются по тем же правилам ownership, regular
  file, link count и mode, что нынешний `profiles.toml`.
- Watcher следит за основным файлом и всеми включёнными фрагментами, включая
  атомарную замену и повторное создание родительских каталогов. Новая
  композиция принимается целиком только после успешной загрузки и проверки.
  При ошибке продолжает работать последний корректный вариант.
- Ошибка отдельной логики обрабатывается нынешним supervision и не останавливает
  другие наборы. Диагностика содержит файл, item, widget и имя привязки.

Известная несовместимость root-owned системных executable с UID mapping
командного backend не устраняется изменением формата наборов. Новые адаптеры
не ослабляют проверку владельца и не скрывают эту ошибку.

## Миграция и критерии готовности

Встроенные наборы `app-actions`, `media`, `controls`, `capture`, `hyprland`,
`command-deck` и кнопочные наборы `omarchy` переносятся на файлы без изменения
их действий, размеров, panel policies и grants. Appearance provider Omarchy
остаётся самостоятельным провайдером. Примеры сторонних/native плагинов
сохраняют старый контракт.

Готовность проверяется поведением:

1. Каждый встроенный набор имеет отдельный файл; манифест перечисляет их явно.
2. Добавление второго Browser-набора и перестановка его кнопок работают с тем
   же неизменённым Wasm. Наборы могут одновременно иметь разное состояние.
3. Неверные action/state bindings, типы, IDs и пути отвергаются до запуска UI.
4. Controls и Media сохраняют непрерывное взаимодействие, отмену контакта,
   подписки и асинхронные ответы. Layout не содержит системных команд.
5. Hot reload профилей/фрагментов атомарен; ошибка оставляет прежнюю композицию.
6. Изменение/подмена файла набора после установки выявляется package/store
   проверкой, как изменение Wasm. Системный запрос без grant/activation
   отвергается и для нового runtime.
7. Старые конфигурации и plugin worlds проходят существующие regression tests.
   Дополняются focused unit/integration/replay tests схемы, независимости
   экземпляров, событий слайдера и sealed transport. Запускаются workspace
   tests, fmt/clippy и применимые acceptance/security campaigns.

Не вводятся редактор наборов, произвольные скрипты в TOML, runtime-наследование
состояния, новые разрешения «на всё» или зависимость от Arch/Omarchy.
